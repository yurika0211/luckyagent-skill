# Work Entropy

把用户的任务直接变成可追溯的工作记录，不要求用户先填写任务卡。资料来源以当前指令、仓库 STATUS、指定笔记、URL、diff 和可访问的当前聊天为准；不要假装读到了未接入的其他聊天或后台活动。

## 三种指标必须分开

- 项目/任务模型熵：事实和决策尚存的候选解释；等概率模型使用 log₂(N)。去重后的求和只是工程近似，不是真实整个项目的联合熵。
- 个人剩余负荷：原子点预算 × (1 − 证据等级)，单位“熵点”。未测不等于不会；证据等级不是概率，不能用二元掌握熵代替它。
- 交付：工作包的验收状态。文档存在、AI 产物或自动测试通过可以证明交付，不能自动证明用户理解。

开始评估或修改口径时读 [model.md](references/model.md)。要写入事件、计时或运行 CLI 时读 [data-schema.md](references/data-schema.md)。有数字就用脚本计算，不凭聊天语气报一个掌握百分比。

## 执行方式

1. 从任务中推断范围、交付物和验收条件，提出一条完整原子样品。把找不到的信息标为未知。用户已经授权落地时，继续完成已授权范围，不因样品流程再要求批准。
2. 在唯一的个人账本中登记 project、task、atom、work，再建立基线。相同知识点跨任务使用 atom.link；不重复创建来刷进度。只登记原子叶子，不把父项与子项重复计分。
3. 按新增证据更新：事实/决策用 atom.resolve，用户的复述或实际行动用 atom.assess，交付用 work.verify。每条都写真实证据引用与判定理由。
4. 确认区间、原子证据和时间范围匹配后才计算效率。没有真实时间数据就展示缺失原因，不补造历史时间。
5. 预测时读取同类型已完成任务样本；不足时不给 P50/P85。可使用用户明确给定的速率区间生成“情景”，但不能标成学习到的个人效率。

## 记账入口

安装目录下的 scripts 均只依赖 Python 标准库；运行环境为 Python 3.10+、Linux/WSL/macOS（使用文件锁）。数据默认在 `~/.local/share/work-entropy/events.jsonl`，不存进 Skill 安装目录。正常工作共用一个个人账本；`--store` 用于独立使用者、样品或验证环境，不能为每个任务新建计时库后相加工时。

```bash
python3 "$HOME/.codex/skills/work-entropy/scripts/ledger.py" init
python3 "$HOME/.codex/skills/work-entropy/scripts/ledger.py" audit
python3 "$HOME/.codex/skills/work-entropy/scripts/report.py" status --project PROJECT_ID
```

复杂事件将准确 JSON 写进临时文件，用 `ledger.py event TYPE --data-file PATH`，不要把长文本嵌进 shell。始终提供 `--source-ref`；从聊天或外部事件导入时用稳定的 `--key`，同一个来源重放不得重新计分。

默认自动选用此 Skill，但计时须有明确事件依据。用户让 AI“开始做”不等于用户本人已开始专注，不能因此自动开启人的计时器。

## 时间规则

- 用户明确“我开始/暂停/切换到某主题”时，读取当前时钟，用 focus start/pause/switch，保存任务、主题、活动类型及相关原子点。
- 读代码、讨论和修改同一交付物可归同主题；换成另一目标就切换。人工活动检测只能建议分类，不能凭键盘静默断定没有思考。
- 只有聊天消息时间差时，最多导入未确认、estimated 区间。禁止把第一条到最后一条消息之间全部算作专注。
- 不把未结束计时器自动延长为有效工时。对漏停、估计和冲突区间用更正事件核对，不能悄悄截断或归零。
- task.coverage 表示已有依据确认该任务工时记录完整；不能仅因系统里没有其他时间就自动设 true。已结束区间合并去重；不同主题冲突部分不进入可靠速率。

## 状态与进度规则

证据等级只有 0、0.25、0.5、0.75、1。0.25 需要能辨认对象；0.5 需要准确解释；0.75 需要新场景应用；1 需要满足该原子点预先写定的验证条件。未测默认 0 个已验证积分，但标签保持“未测”。不因用户重复问问题而扣分；有效反例可能是高质量理解证据。

自动测试结果本身不用于 atom.assess。用户独立完成或解释了什么，引用 user_message/observed_action；复制助手解释或一句“懂了”不够。已有个人证据失效时明确更正或 reopen，净进度允许下降。

事实没有答案与用户没理解是不同问题：用户可以充分理解“目前缺少源键契约”，但项目的源键事实仍未确定。必要时分成事实点和能力点，并关联而非互相代替。

新增范围单独显示，不静默重算旧基线分母。baseline.add 新版本仅是度量快照，不是额外审批流程。保存旧版本，必要时用 status --baseline ID 对比。

## 预测与报告

报告只展示当前范围。项目有未建模模块时列出来，不宣称得到了全项目真实总熵。默认正文最多展示 5 个关键点，完整数据保留在 JSON。

任务有真实 receipt 时间才计算日历耗时；只知道日期时保留 received_date，不能补成午夜来冒充准确时间。窄均速率要求完整的确认区间、正确信息来源及所有正增益的配对工时。不能用一小时记录除整天所得的知识。

整包任务包含执行或 mixed 时间时，不把它的速率当作纯澄清速率。decomposed 预测只用纯理解/验证/返工样本，另加明确且不重叠的执行估计；whole 模式仅用于一个同规模工作包，不再加执行时间。whole 采用已投入工时后的条件剩余样本，超过历史范围就提示数据不足。

10 个同项目、同类型有效闭环样本只是第一版经验分位数的工程门槛，不是统计保证。P50/P85 一律先标“未校准”。无明确每日可投入时间时不换算日历日期；固定每日投入的结果只是情景，不包含未建模的等待、依赖并行或范围增长。

forecast --record 保存不可回填日期的预测快照；后续 calibration 比较预测之后实际投入的时间。缺完整工时、范围变化等不匹配预测要排除并说明，不能对自己编出的概率作自我验证。

## 完成当前任务时

先核对必需工作包的验收，再 task.complete。真实理解进度可以与交付进度不同。需要积累历史样本时明确调用 task.sample；失效的基线、个人证据或工时更正会使旧样本不再用于预测。

对当前问题给出结果、证据缺口和一个可执行下一步，不把不可靠估计当成用户能力评价。禁止仅为填满报告而追问一串材料；资料不足时继续可做的工作。

## 维护验证

```bash
python3 -B -m unittest discover -s "$HOME/.codex/skills/work-entropy/scripts" -p 'test_work_entropy.py' -v
python3 "$HOME/.codex/skills/.system/skill-creator/scripts/quick_validate.py" "$HOME/.codex/skills/work-entropy"
```

测试只使用临时合成账本，不能把合成学习记录混入真实个人统计。事件模型/公式变更时提升计量版本并明确迁移；不静默用新公式重写旧版结论。
